# 03 · 必须避开的坑（真实案例复盘）

每一个坑都是这次开发中**真实踩过并修好**的。格式统一：
**现象 → 日志证据 → 根因 → 正解 → 通用教训**。

这些坑的共同特征：**编译期全部看不出来**。所以它们的价值不在于"记住答案"，
而在于"认出这类形状"。

---

## 坑 1：把 `const` 当字段写

### 现象
游戏启动直接失败，弹错误框并退出。整个模组形同虚设。

### 日志证据
```
[ERROR] Encountered error on game startup! Attempting to show error dialog
[ERROR] System.FieldAccessException: Cannot set a constant field.
   at System.Reflection.MdFieldInfo.SetValue(...)
   at Ascension11.AscensionLevelRegistry.RaiseMaxAscensionAllowed()
   at Ascension11.Patches.AscensionCapacityPatches.ModelDbInitPostfix()
   at MegaCrit.Sts2.Core.Helpers.OneTimeInitialization.ExecuteEssential_Patch2()
   at MegaCrit.Sts2.Core.Nodes.NGame.GameStartup()
```

### 根因
```csharp
public const int maxAscensionAllowed = 10;   // 反射 IsLiteral = True
```
`const` 的值被编译器**内联**到每一个使用处，运行时根本没有字段槽位。
我的代码却用 `AccessTools.Field(...).SetValue(null, 11)` 去写它。

而且这个异常发生在 `ModelDb.Init` 里，冒到 `NGame.GameStartup()` 就**中止启动**。

### 正解
1. **不要写它**。全局扫描确认 `maxAscensionAllowed` 根本没被任何代码引用（死代码）。
   真正的上限是散落各处的字面量 `10`，只能改 IL（见 [02 §1.5](02-游戏API实证清单.md#15-上限-10-到底写在哪il-实录共-13-处)）。
2. 顺带一个更重要的习惯：**`ModelDb.Init` 里的任何代码都不能抛异常**。
   现在整个入口用 try/catch 包住，补丁失败最多让功能不生效，不会让游戏起不来。

### 通用教训
> 判断"能不能改"不要看它长什么样，要**实测** `IsLiteral` / `IsInitOnly`。

```csharp
var f = type.GetField("maxAscensionAllowed", BindingFlags.Static|BindingFlags.Public|BindingFlags.NonPublic);
Console.WriteLine($"IsLiteral={f.IsLiteral} IsInitOnly={f.IsInitOnly} Value={f.GetRawConstantValue()}");
```

`IsLiteral=True` → 只能改 IL。`IsInitOnly=True` → 通常可以在运行时写（但游戏可能已内联读取）。

## 坑 2：把 BaseLib 生成的枚举值当数字用

### 现象
进阶 11 逻辑全都不生效；日志里出现一个莫名其妙的负数枚举值。

### 日志证据
```
[Ascension11] Ascension level 11 registered as AscensionLevel.-648373254 (generated enum value -648373254).
```

### 根因
BaseLib 的 `[CustomEnum]` **不是**按"下一个整数"分配值的，而是生成一个**哈希值**：

```
[BaseLib] Generated KeyGenerator for enum …AscensionLevel with starting value 11 | IsFlag: False
```

我写的是 `if ((int)level == 11)` 来判断"是不是我这一阶" —— 永远为 false。

### 正解
枚举值只当**身份标记**，等级号永远用自己定义的常量：

```csharp
public static AscensionLevel EmpoweredElites;   // [CustomEnum("EmpoweredElites")]

public const int Level = 11;                                       // ← 等级号只用这个
public static bool IsOurLevel(AscensionLevel l) => _resolved && l == EmpoweredElites;   // 按身份比较
```

并且在 patch 里把枚举翻回数字：
```csharp
__result = __instance._level >= AscensionLevelRegistry.Level;
```

另外，**"是否已生成"不能只看 `!= 0`**（哈希值可能碰巧为 0），要防"读得太早"：
本模组把读取时机放在 `ModelDb.Init` 之后。

### 通用教训
> 别人生成的标识符，**不要假设它的数值有语义**。要么用它的名字/身份，要么用你自己的常量。

## 坑 3：面板能选 11，进局却是 10

### 现象
进阶面板显示 11、文案也对，但进游戏左上角显示"进阶 10"，A11 的效果一个都没生效。

### 日志证据
没有报错。**这是最糟的一类 bug——完全静默。**
只能靠主动打印四个位置的值才发现。

### 根因
进阶等级在游戏里存在**四个地方**（见 [02 §1.6](02-游戏API实证清单.md#16-进阶等级在游戏里的四个存放位置)）。
我只改了"面板"那一个。而……

```csharp
// StartRunLobby.SetSingleplayerAscensionAfterCharacterChanged
MaxAscension = GetMaxAscensionAcrossAllCharacters();               // = Max(所有角色.MaxAscension) = 10
Ascension    = Math.Min(stats.PreferredAscension, MaxAscension);   // Min(11, 10) = 10
```

### 正解
补 `CharacterStats.MaxAscension` 的 getter（**唯一收口点**，大厅和面板都读它）：

```csharp
[HarmonyPatch(typeof(CharacterStats), nameof(CharacterStats.MaxAscension), MethodType.Getter)]
[HarmonyPostfix]
private static void MaxAscensionGetterPostfix(ref int __result) {
    if (__result < 11) __result = 11;
}
```

**关键技巧：找到"唯一收口点"而不是逐个调用点打补丁。**
做法是对目标属性做**全局读者扫描**（见 [04 §1 的"谁引用了它"脚本](04-调试与验证工作流.md#11-找出谁读写了某个成员)），
列出所有读者，再判断哪个是公共上游。

`CharacterStats.MaxAscension` 的好处还在于：**只改返回值，不写存档**。
玩家存档里的 `MaxAscension: 10` 保持原样，卸载模组后完全兼容。

### 通用教训
> 当"界面显示对了但行为不对"时，**第一件事是把相关的所有状态值一起打出来**。
> UI 显示的值 ≠ 逻辑生效的值，中间往往隔着一层 `Min()` / `Clamp()` / 归一化。

## 坑 4：进精英战斗直接卡死

### 现象
普通战斗一切正常；一进精英房，画面停住，游戏完全无响应（进程没崩，只能强杀）。

### 日志证据
```
# 普通战斗：钩子正常触发
[Ascension11] Ascension 11 elite check: '…CORPSE_SLUG.name' skipped (not an elite room; mapPoint=Monster, room=Monster).
[Ascension11] Ascension 11 elite check: '…TOADPOLE.name'  skipped (not an elite room; mapPoint=Monster, room=Monster).

# 进精英房后：没有任何 granted 行，日志到此为止
[INFO] Creating NCombatRoom with mode=ActiveCombat encounter=TERROR_EEL_ELITE.
```

### 根因
我自己写出来的**死锁**。原代码：

```csharp
private static object AfterAddedToRoomPostfix(object __result, MonsterModel __instance) {
    var awaiter = task.GetAwaiter();
    awaiter.OnCompleted(() => { /* 加力量 */ });
    awaiter.GetResult();      // ← 就这一行
    return task;
}
```

`PowerCmd.Apply` 是**异步命令，需要游戏主循环继续推进才能完成**。
而 postfix 跑在**主线程的游戏循环内部**，`GetResult()` 把主循环卡住了 —— 命令永远完不成，游戏冻结。

> 注意：**原版怪物在同一个钩子里 `await PowerCmd.Apply` 是没问题的**（我 dump 过 `MechaKnight`）。
> 区别在于游戏自己是 `await`（让出线程），我是 `GetResult()`（阻塞线程）。

### 正解
走**同步内部路径**，全程不 await：

```csharp
var power = ModelDb.Power<StrengthPower>().ToMutable();   // 见坑 5
power.ApplyInternal(creature, 1, silent: true);
```

`ApplyInternal` 是纯同步代码（设 Owner → 应用数量 → 挂到生物身上）。

### 通用教训
> **游戏主线程里永远不要同步等待异步命令。**
>
> 判断一个命令能不能同步等：看它内部有没有 `await`（特别是 await 钩子 / 玩家选择 / 动作队列）。
> 有 → 要么在能 await 的地方 await，要么找同步内部方法。
>
> 另一个信号：**"进某个特定场景才卡死"** 通常就是死锁或死循环，而不是逻辑错误。

## 坑 5：不卡了，但力量没加上

### 现象
精英战不再卡死，但敌人身上没有力量图标，伤害也没变。

### 日志证据
```
[INFO] Creating NCombatRoom with mode=ActiveCombat encounter=TERROR_EEL_ELITE.
[ERROR] [Ascension11] Failed to apply Ascension 11's elite Strength.
System.NullReferenceException: Object reference not set to an instance of an object.
   at MegaCrit.Sts2.Core.Models.PowerModel.SetAmount(Int32 amount, Boolean silent)
   at MegaCrit.Sts2.Core.Models.PowerModel.set_Amount(Int32 value)
   at MegaCrit.Sts2.Core.Models.PowerModel.ToMutable(Int32 initialAmount)      ← 就是这
   at Ascension11.Patches.EliteStrengthPatches.GrantStrength(Creature creature)
```

### 根因
`PowerModel.ToMutable(int initialAmount)` 会在克隆体**还没有 Owner** 时调用 `SetAmount`，
而 `SetAmount` 内部解引用 `Owner` → 空引用。**无参的 `ToMutable()` 不走这条路。**

### 正解
```csharp
var power = ModelDb.Power<StrengthPower>().ToMutable();   // 无参！克隆体数量为 0
power.ApplyInternal(creature, 1, silent: true);           // 一次性完成 Owner + 数量 + 挂载
```

这正好等价于 `PowerCmd.Apply` 内部的顺序。**看内部实现，不要只看 API 名字。**

### 通用教训
> 同名重载语义可能完全不同。**不确定就在 IL/反编译里看它到底做了什么。**
>
> 另一个点：这行 `NullReferenceException` 之所以能一眼定位，是因为**堆栈里有行号**
> （我发布的 `.pdb` 跟 `.dll` 一起放进了 `mods/<ModId>/`）。
> **发布时保留 `.pdb`**，运行时异常就有文件名+行号，排查速度差一个数量级。

## 坑 6：本地化目录名不等于模组 id

### 现象
进阶面板上标题显示成 `LEVEL_11.title`、描述显示成 `LEVEL_11.description` 原文。

### 日志证据
```
# 游戏合并了 11 张模组表，但没有我的 ascension.json
[INFO] Found loc table from mod: zhs cards.json. Merging with base loc table
[INFO] Found loc table from mod: zhs powers.json. Merging with base loc table
[INFO] Found loc table from mod: zhs static_hover_tips.json. Merging with base loc table
...
```

### 根因
游戏找模组文本的路径是**硬编码拼接**（IL 实录）：

```
"res://" + <manifest.id> + "/localization/" + <language> + "/" + <file>
```

我的资源目录叫 `Ascension11Resources`（照抄别的模组），游戏永远找不到。

### 正解
把资源目录改名成模组 id，并在 `csproj` 里对应：

```xml
<ResourcesDir>Ascension11</ResourcesDir>   <!-- 必须等于 manifest id -->
```

并在部署脚本里**断言产物内容**，让这个静默失败变成显式失败：

```powershell
$t = [Text.Encoding]::UTF8.GetString([IO.File]::ReadAllBytes($pck))
if (-not $t.Contains("Ascension11/localization/zhs/ascension.json")) { throw "pck 缺少本地化路径" }
```

### 通用教训
> **照抄别人的目录约定是危险的**——它可能只是碰巧生效，或者依赖了你没注意的机制。
>
> 界面上出现**原始 key**（`xxx.title` 这种）时，一律是"查不到 key"，
> 而不是"文案写错了"。**这是 100% 可靠的判别信号。**

## 附：这些坑的共同形状

回头看，6 个坑可以归成 3 类。**认出类别，就能提前预防：**

| 类别 | 特征 | 预防手段 |
| --- | --- | --- |
| **A. 对游戏内部结构的错误假设** | 坑 1（const）、坑 2（枚举值）、坑 6（目录名） | 动手前**实测**：反射 dump、IL dump、看内部实现。不要照抄别人的写法 |
| **B. 状态有多份，只改了一份** | 坑 3 | 对目标属性做**全局读者扫描**，找"唯一收口点"；把相关值都打日志 |
| **C. 线程/异步模型搞错** | 坑 4、坑 5 | 主线程不阻塞；不猜重载语义，看 IL |

### 交付前自检清单

- [ ] 所有要改的常量，都用反射确认过 `IsLiteral` / `IsInitOnly`
- [ ] 所有"新增的标识"（枚举/表名/id），都没有假设数值或名字有语义
- [ ] 每个"显示对了但行为不对"的地方，都把上游状态值打出来核对过
- [ ] 补丁里没有任何 `.GetResult()` / `.Wait()` / `.Result`
- [ ] 所有改 IL 的地方，都用校验器跑过（改了 N 处、剩 0 处）
- [ ] `.pck` 内容断言通过
- [ ] `.pdb` 和 `.dll` 一起部署（异常有行号）
- [ ] 每个补丁都有"失败可诊断"的日志路径
