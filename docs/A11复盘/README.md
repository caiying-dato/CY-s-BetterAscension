# 杀戮尖塔 2 模组开发经验（Ascension 11 "精英强化" 项目复盘）

本目录是一次完整模组开发的复盘：从零写一个**扩展进阶系统**的模组，到它可以正常启动、正确显示、效果生效。
记录的重点不是"我写了什么代码"，而是**哪些地方看着合理但其实是错的、以及怎样才能在交付前发现它们**。

- 参考产出：`D:\ds-pro\塔2更好的进阶难度`（模组 ID `Ascension11`，v0.1.4）
- 游戏版本：`v0.111.0` · BaseLib `3.4.7` · Harmony `2.4.2` · MegaDot `4.5.1-m.14`
- 全部结论都来自**本机 `sts2.dll` 的反编译/IL dump**，不是猜的；无法验证的都标了 **UNVERIFIED**

## 这份文档解决什么问题

第一版交付的模组**能编译、能部署、模组列表里也能看到**，但：

| 症状 | 真实根因 |
| --- | --- |
| 游戏启动崩溃，弹错误框 | 反射写了一个 `const` 字段 → 未捕获异常冒到 `NGame.GameStartup()` |
| 界面显示 `LEVEL_11.title` 原文 | 模组本地化目录名不等于模组 id，游戏永远找不到 |
| 选了进阶 11，进局却是进阶 10 | 大厅用 `Min(Preferred, MaxAscension)` 夹取，存档里 `MaxAscension=10` |
| 进精英战斗直接卡死 | 在游戏主线程里 `GetResult()` 同步等待异步命令 |
| 不卡了，但精英没加力量 | `PowerModel.ToMutable(int)` 在 Owner 为空时设数值 → 空引用 |

**这些错误没有一个能在编译期发现。** 这份文档就是把它们逐一变成"下次能在 5 分钟内定位"的东西。

## 三条最重要的结论

如果只记三件事：

### 1. LLM/人都容易犯的错：`const` 字段改不了

```csharp
// AscensionManager 里这个不是字段，是编译期常量
public const int maxAscensionAllowed = 10;
```

反射显示 `IsLiteral=True`。编译器把 `10` **内联**到了每一个使用处，运行时根本没有槽位可写。
`FieldInfo.SetValue` 会抛 `FieldAccessException: Cannot set a constant field.`。
**要改它只能改 IL。**（详见 [03](03-必须避开的坑.md#坑-1把-const-当字段写)）

> 推论：判断"能不能改"不要看它长什么样，要 `IsLiteral` / `IsInitOnly` 实测。

### 2. "显示的值"和"生效的值"很可能不是同一个

进阶等级在游戏里有**四个**独立存在的地方：

```
NAscensionPanel.Ascension        —— 面板上显示、玩家选的
StartRunLobby.Ascension          —— 联机大厅同步的；选定角色时被 Min(Preferred, Max) 夹取
RunState.AscensionLevel          —— 真正进入运行局的（int）
AscensionManager._level          —— 运行局里所有 HasLevel 判断的依据
```

**只改一个不够。** 我最初只改了第一处，于是"面板显示 11、实际跑在 10"。
排查这类问题时，第一件事是把四个值分别打出来。（详见 [03](03-必须避开的坑.md#坑-3面板能选-11进局却是-10)）

### 3. 游戏主线程里**永远不要**同步等待异步命令

```csharp
// 会死锁：PowerCmd.Apply 需要主循环推进，而你把主循环卡住了
awaiter.GetResult();
```

补丁跑在主线程的游戏循环内。任何"等一个需要主循环才能完成的 Task"的写法都会**整个游戏冻结**。
要么在能 await 的地方 await，要么走同步内部路径。（详见 [03](03-必须避开的坑.md#坑-4进精英战直接卡死)）

## 配套的验证工具（可直接复制到新项目）

这次最大的收获是**把"猜"换成了"验"**。三个工具，全部零依赖、可离线跑：

| 工具 | 作用 | 位置（本模组工程内） |
| --- | --- | --- |
| **IL 校验器** | 把 Transpiler 的重写逻辑跑在**真实 `sts2.dll` 的 IL** 上，断言"该改的都改了、没有残留" | `tools/TranspilerCheck/` |
| **API dumper** | 反射/IL dump 任意游戏类型的成员与方法体，用来查签名、查 `IsLiteral`、查谁调用了谁 | `tools/ApiDump/` |
| **部署断言** | 部署时断言 `.pck` 里确实含有预期的本地化路径，防止"目录名写错"这类静默失败 | `deploy.ps1` |

IL 校验器抓住过一个真实的、编译器完全看不出来的 bug：转译器声称改了 9 处常量，实际只改对 3 处、
另有 2 处压根没匹配上——**那 2 处会让进阶 11 在读档时被夹回 10**。跑一次校验器只要几秒，进游戏试一次要几分钟。

## 一句话方法总结

> **凡是能在本地验证的，就不要靠猜；凡是会静默失败的，就让它大声报错。**

具体落成四条习惯：

1. **改任何游戏内部状态前，先 dump 出它的真实形态**（`IsLiteral`？`get` 还是 `set`？谁调用它？）
2. **不确定的接口不要硬写调用，先探测再调用，并把探测结果打进日志**
3. **每个补丁都写成"失败可诊断"**：匹配不到就明确 warn，而不是静默不生效
4. **能自动断言的（IL 改动、打包内容）就写成脚本**，每次改完先跑脚本再进游戏
